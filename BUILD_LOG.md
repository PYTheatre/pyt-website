Fix — nav logo squashing at mid/narrow widths (2026-08-19)
Goal (PM): since the logo moved down into the hero on the homepage, the nav-bar logo on every OTHER page is the only way back home — but PM reported it looked visibly squashed/distorted at certain widths (both a "squashed" mid-size desktop width and on mobile), making it look broken rather than like a working home button.
Root cause: a site-wide reset (`img { max-width: 100% }` in global.css, there to stop images ever overflowing their container) was fighting with the logo's own sizing rule (a fixed `height: 44px/54px; width: auto;`, there to keep it correctly proportioned). Whenever the header ran low on horizontal room — the logo, Register, Donate, ES, and (on mobile) the hamburger button all sit in the same row and compete for space, and nothing was protecting the logo from being squeezed — its flex box could shrink narrower than the image actually needed. Once that happened, the `max-width: 100%` reset clamped the image's WIDTH down to fit the shrunk box while its HEIGHT stayed locked at 44px/54px, and that mismatch between a fixed height and a clamped width is what visibly squashed it.
Built (2 files):
  - src/components/Logo.astro (EDIT, site-wide component) — added `flex-shrink: 0` to the logo's own wrapping element, so its box can never be squeezed narrower than the image needs in the first place — the actual fix, since it stops the `max-width: 100%` clamp from ever triggering rather than trying to patch around it after the fact.
  - src/components/Header.astro (EDIT, site-wide component) — as a safety net for the rare case there's still genuinely not enough horizontal room (e.g. very narrow phones), added `flex-wrap: wrap` to both `.header-inner` and `.header-actions`, so any excess content wraps onto a second line within the header instead of squeezing the (now-protected) logo or overflowing off-screen. Previously the logo silently absorbed that squeeze and visibly warped; now the header just becomes two rows instead when it needs to.
Tested: build stayed at 32 real pages. Navbar: fix — Tickets button not showing blue, ES toggle too washed out (2026-08-19)
Goal (PM): caught live that the Tickets button rendered as a plain white pill (no blue, no ticket shape) and the ES toggle was barely visible against the dark bar.
Root cause, Tickets button: CSS specificity, not a deploy issue. Astro automatically appends its own scoping attribute to EVERY class in a selector, not just the last one — so ".nav-wide .pill" doesn't compile to "2 classes" worth of specificity, it compiles to 4 (class + attribute, twice), while ".tickets-btn" alone is only 1 class + 1 attribute = 2. The nav-wide rule was winning by a wide margin, silently overriding the blue background/text color back to the plain default every other nav pill uses. Confirmed by inspecting the actual compiled CSS output, not just the source.
Root cause, ES toggle: the button sits in .header-actions, OUTSIDE the .nav-wide container, so the ".nav-wide .pill" rule that gives every other nav item its bright white color never reaches it at all — it was falling back to the base .pill class's default color (--ink-soft), which is a muted gray tuned for light-background contexts elsewhere on the site, not this dark bar.
Built (1 file):
  - src/components/Header.astro (EDIT, site-wide component) — .tickets-btn's background/color now use !important, matching the approach already used for the mobile version (which had this same protection from the start and was unaffected by this bug) — chosen over trying to out-calculate Astro's auto-injected specificity, which is what caused the miscalculation in the first build of this feature. .lang-toggle now sets its own color/background explicitly (also with !important, for the same certainty) instead of relying on inheriting from a rule that doesn't actually reach it, and gained a faint border (matching the hamburger button's existing border treatment) so it reads as a real button rather than plain dim text.
