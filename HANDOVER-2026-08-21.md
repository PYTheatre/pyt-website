## 0. READ THIS FIRST — the five rules that matter most

These come from the PM directly and from mistakes actually made. Follow
them without being asked.

1. **Mock up before building anything visual.** Generate a real PNG
   image file (Pillow) and present it. **Never** use the interactive
   widget tool — it does not render on the PM's machine. This applies
   to layout, colour, spacing and type changes.

2. **Never paste raw code into the chat.** Hand off work as *files*
   (`present_files`) plus GitHub links. The PM pastes by hand.

3. **Give a GitHub link for EVERY file, every time.** Not a folder, not
   "the usual place" — a specific link per file. The PM has had to ask
   for missing links more than once. Formats:
   - edit an existing file:
     `https://github.com/PYTheatre/pyt-website/edit/main/<path>`
   - create a new file:
     `https://github.com/PYTheatre/pyt-website/new/main/<folder>`
   - upload:
     `https://github.com/PYTheatre/pyt-website/upload/main/<folder>`
   - delete: link to the file's page, then "trash icon → Commit"

4. **If a batch contains a NEW file that others import, say so loudly
   and put it first.** Number the steps. A missing new file breaks the
   whole build, and this has happened.

5. **Verify what is actually live on GitHub before assuming anything.**
   `git fetch origin main && git reset --hard origin/main`, then build.
   Do not trust that the last batch landed — several times it hadn't,
   or had landed only partly.

## 1. HOW TO START A SESSION

```bash
cd /home/claude
git clone --depth 50 https://github.com/PYTheatre/pyt-website.git
cd pyt-website && npm install --no-audit --no-fund
rm -rf dist && npm run build
find dist -name index.html | wc -l
```

- The clone works without credentials (public repo).
- **Astro's "31 pages built" summary UNDERCOUNTS.** Always count
  `index.html` files instead. **The correct number right now is 33**
  (was 32 before the Volunteer page; see §2).
- Builds take 5–15s. Use `timeout 150 npm run build`.

### Deployment
Cloudflare Pages auto-deploys from `main`. A failed build does **not**
take the site down — Cloudflare keeps serving the last good build. That
also means **a broken build can go unnoticed**; if the PM says "did that
work?", check their Cloudflare deployments screen or just build the live
repo yourself.

## 4. THINGS THAT WILL BITE YOU (learned the hard way)

**Grepping built HTML gives false positives.** Class names appear in
the `<style>` block as well as the markup. `grep -c "some-class"` will
report matches on pages that don't render the element at all. **Always
parse with `HTMLParser` and skip `<style>`.** This produced two wrong
conclusions in this session before being caught.

**Decap CMS caches its config in the browser.** After ANY `config.yml`
change, new fields will not appear until a hard refresh (Cmd+Shift+R)
or an incognito window. **Tell the PM this every single time** — they
lost time to it twice because it wasn't mentioned.

**`required` is the default in Decap.** A field without
`required: false` cannot be cleared, and the PM will report "the CMS
won't let me delete this". Hit twice (phone number, impact heading).
When adding a field, decide deliberately.

**Clearing a field is only half the job.** The page must also *hide*
the element when the value is blank, or you get a stray label with
nothing under it.

**Astro ternaries return ONE element.** `{cond ? (<p/><Foo/>) : null}`
fails to build. Wrap in `<>…</>`. Broke the build twice this session.

**Python `round()` ≠ JavaScript `Math.round()`.** Python uses banker's
rounding: `round(74.5)` is 74, JS gives 75. A mockup showed 74% where
the site showed 75%. Use `math.floor(x + 0.5)` in mockups.

**Downloaded files lose awkward filenames.** `[...slug].astro` arrives
as something else; `.ts` files get treated as video by macOS; a file
with no extension (`_redirects`) may not open at all. **For any file
with brackets, no extension, or an odd extension, tell the PM to use
"Create new file" on GitHub and paste, rather than upload.** This
caused four consecutive failed deploys this session.

**Cloudflare: a real page beats a redirect.** See §2.

## 6. PM PREFERENCES AND DESIGN DECISIONS

**Typography**
- **Baloo 2 is used in exactly two places**: the home page hero
  headline, and the BE KIND / BE PREPARED / BE BRAVE words. Discovery
  card titles/subtitles also use it (PM confirmed this stays).
  Everything else is **Archivo Black**.
- Baloo 2 **has no italic**. `font-style: italic` gives a
  browser-synthesised slant. The PM knows and accepts this.
- Body copy stays **Source Sans 3**. The PM once said "everything
  should be Archivo Black" — that was about headings. Archivo Black has
  one very heavy weight and is unreadable as body copy. This was
  flagged and accepted.
- All text is **black** unless it sits on a dark/coloured ground, where
  it goes light for contrast.

**Colour**
- Panels: pale lilac `#efeaf8` (`--paper-warm`). Page background: white.
- The PM dislikes grey text and warm off-white.
- **Pastels fail contrast on pale grounds** (1.5–2.2 vs a 3.0 minimum
  for large display text). Pastels are only used on the dark band (stat
  boxes). Deep brand colours are used on lilac. **Check contrast before
  proposing a colour** — this changed a decision once already.

**Layout**
- Section gaps on the home page are all 8rem. Keep them even.
- The PM notices uneven spacing and unbalanced elements quickly, and is
  usually right; measure rather than assume.

**Content and CMS**
- **Everything should be editable in the CMS.** This has come up
  repeatedly. When building anything with text in it, make it a field.
- Prefers optional fields that hide cleanly when blank.
- Prefers automatic behaviour over more CMS choices (e.g. colours that
  rotate by position rather than a colour picker per item).
- Wants redundant CMS fields cleaned up when a redesign makes them
  obsolete.

**Working style**
- Works in short bursts, often pausing mid-upload. **Always re-verify
  live state when they return.**
- Sends screenshots to report problems. Read them carefully — they are
  usually pointing at something real.
- Appreciates being told when something they asked for won't work, and
  why, with the alternative.

## 7. ARCHITECTURE NOTES

- **`src/lib/`** holds shared helpers: `markdown.ts` (renderMarkdown),
  `imageFocus.ts` (focus % → CSS position), `showLabels.ts` (stored
  production_type → visitor-facing label).
- **`production_type` values are load-bearing.** Stored as `"Musical"`
  and `"Studio Production"`; the Musicals and Studio Shows pages filter
  on them. The CMS *labels* say "Center Stage Musical" / "Studio Show"
  but the stored values are unchanged. **Never rename the values** —
  it would silently empty both pages.
- **`PageHeroImage.astro`** matches on the EXACT page path. It used to
  cascade to child pages; that was removed because it forced a hero
  onto every Stories on Stage production page. It also accepts
  `image` / `focus` / `alt` props, used by staff-created pages.
- **`nav-menu.json`** drives the whole nav. Staff-created pages can
  append themselves to a dropdown; duplicates are skipped by URL.
- **`_redirects`** in `public/` is Cloudflare's redirect file. One rule
  per line: `<old>  <new>  301`.

## 8. TESTING STANDARD EXPECTED

For every batch:
1. Build and confirm the page count.
2. **Parse the built HTML with `HTMLParser`** (not grep) to confirm the
   change actually rendered.
3. **Empty-safe test**: blank every new/changed CMS field and rebuild.
   Nothing should crash, and no empty elements or stray labels should
   render.
4. **Edge cases**: 0, maximum, over-maximum, and invalid input where
   numbers are involved.
5. **Restore and diff** the test data byte-for-byte.
6. Check the *compiled* CSS/JS in `dist/`, not just the source.
7. Copy files to `/mnt/user-data/outputs/` and **diff each against the
   tested source** before presenting.

Report honestly what was verified and what only the PM's own eyes can
confirm (real rendering, feel on a phone, third-party services).
