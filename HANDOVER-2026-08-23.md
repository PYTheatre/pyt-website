## 2. WORKING RULES — FOLLOW WITHOUT BEING ASKED

These are the PM's standing rules. They were restated at the start of the last
session and enforced throughout. Breaking them causes real rework.

1. **MOCKUPS: for anything visual, produce an actual PNG and show it.**
   Do NOT use the interactive widget tool — it does not render on their end.
2. **LABEL FILES.** If a response contains both a mockup and repo files, say
   explicitly which is which. They have been confused by this before.
3. **NEVER paste raw code into chat.** Give a downloadable file plus a GitHub
   link.
4. **A SPECIFIC GITHUB LINK FOR EVERY FILE IN A BATCH** — edit, create-new,
   upload or delete as appropriate. They have had to ask for missing links
   repeatedly, and it happened again this session ("what about 2–5?"). Never
   write "same links as before".
5. **NEW FILES FIRST.** If a batch contains a brand-new file others depend on,
   say so and number the steps. Always say whether it is safe to stop halfway —
   they work in short bursts.
6. **NEW OR AWKWARD FILENAMES:** for any new file, and anything with square
   brackets, no extension, or an unusual extension, tell them to use GitHub's
   "Create new file" and paste. Downloading and re-uploading mangles the name
   and broke four deploys once.
7. **CMS CACHE:** whenever a batch changes `public/admin/config.yml`, remind
   them to hard-refresh the CMS (Cmd+Shift+R) or use incognito, or new fields
   will not appear.

### Additional preferences learned this session

- **They approve mockups fast and in one line** ("A aligned please and option 1
  for navbar"). Give a clear recommendation and one alternative; do not present
  four options with no steer.
- **They will overrule a recommendation, and that is fine.** When they do, build
  their choice without re-litigating.
- **They send screenshots to report problems.** Read them closely — they are
  usually right about the symptom and the real cause is often deeper than the
  screenshot shows.
- **They notice inconsistency between page types.** Several jobs this session
  came from "this page doesn't match that page".
- **They ask "how do I do this?" when the fix may be theirs.** Distinguish
  clearly between a CMS edit they make and a code file you supply.

## 3. ⚠️ TRAPS THAT HAVE ALREADY CAUSED DAMAGE

### 3.1 The webfont measurement trap — cost a shipped bug

`Archivo Black` loads from Google Fonts, **which is unreachable from the agent
sandbox**. Measuring the nav in a headless browser without it gives a narrower
substitute face and answers roughly **90px too small**.

That happened. A nav breakpoint was set from bad numbers, shipped, and produced
a header that wrapped onto two rows at *every* desktop width. The PM caught it
in a screenshot.

**`document.fonts.check('16px "Archivo Black"')` is NOT sufficient — it returns
`true` for a fallback.** Verify that `[...document.fonts]` actually contains a
loaded Archivo face.

**Working method:** download the real fonts and serve them locally, then inject
an `@font-face` block with `page.add_style_tag()` and await
`document.fonts.ready`. Fonts used: Archivo Black (headings), Baloo 2 (hero and
values), Source Sans 3 (body). All available from the google/fonts GitHub repo,
which the sandbox *can* reach.

**Astro's scoped styles beat injected test CSS.** Overrides in a test
`add_style_tag` need `!important`, or they silently lose and you measure the
unmodified page and believe you tested something. This also happened.

### 3.2 Pasting into GitHub's web editor — took the site down

A file was pasted without selecting the existing content first. The result was a
**493-line file that should have been 248**, with the old body still underneath
and a stray `*---` at line 15. It did not build. **Every subsequent deployment
also failed**, because they were all building the same broken file — which
looked alarming and had one cause.

**Always tell the PM: click into the editor, Cmd+A, then paste**, and give them
a specific expected line count and first line to check before committing.

**Diagnostic that works:** clone `main`, compare each handed-over file
byte-for-byte against what was sent. It found exactly one corrupted file out of
eleven in about a minute.

### 3.3 Over-broad regex edits

A cleanup removed every `eyebrow=` prop across ten page files. Nine were dead —
but `AuditionsPromo` genuinely supports `eyebrow`, and that one should have
stayed. It was caught only by comparing built HTML before and after.

**Before/after HTML comparison is the safety net.** Normalise two things or you
get false positives: the per-build asset hashes (`.a1b2c3d4.css`) and
ContactForm's random element ids (`cf-name-x7k2p9`).

### 3.4 Batch size is itself a risk

A 35-file cleanup was prepared and deliberately cut to 5 files for handover
week. **Thirty hand-pastes carries more risk than the benefit justifies**, and
the cleanup was proven to change nothing visible. The PM agreed. Apply the same
judgement: a large invisible tidy-up is not worth a broken build.

## 8. HOW TO VERIFY WORK ON THIS PROJECT

The method that caught every real bug this session:

1. **Clone `main` fresh and build it.** Never trust that the last session's
   files landed — one of them had not.
2. **Serve `dist/` locally and drive it with a headless browser**, with the real
   fonts injected (§3.1). Measure; do not eyeball.
3. **Sweep pages × widths.** 320 / 360 / 390 / 768 / 1024 / 1119 / 1120 / 1280 /
   1440 / 1920 across a dozen pages catches almost everything. Assert on
   `document.documentElement.scrollWidth - window.innerWidth` for overflow and
   on `.header-inner` height (~83px one row, ~141px wrapped).
4. **For refactors, diff built HTML before and after** and require it to be
   identical, normalising asset hashes and ContactForm ids.
5. **State findings as measurements, not impressions.** The PM responds well to
   "187px against 96px everywhere else" and has twice been proved right by it.
