3. WORKFLOW LESSONS — READ THIS BEFORE SENDING ANY FILES
============================================================
These are hard-won from repeated real mistakes this session, several of which broke the live site. Follow them exactly.

A. How to hand off files (this is the PM's established, confirmed-working preference):
   - For each changed file: (1) a short plain-language line naming what changed, (2) a direct GitHub link, (3) the file itself via present_files (a downloadable/viewable card).
   - EXISTING files → use the pencil-edit link: https://github.com/PYTheatre/pyt-website/edit/main/<path>. The PM opens it, selects all existing text, pastes in the new content from the downloaded file, commits.
   - BRAND-NEW files → use the upload link: https://github.com/PYTheatre/pyt-website/upload/main/<folder>. Edit-links don't work for files that don't exist yet.
   - Do NOT paste raw code into the chat as a giant text/code block. This was explicitly rejected as "terrible... I'm just watching the code appear."
   - Do NOT rely on the interactive Imagine/visualizer widget for mockups — it does not render on the PM's client (confirmed: "i can't see this" for an SVG widget). For ANY mockup, generate a real static PNG (Python + PIL, see the several `gen*.py` scripts used this session for the pattern) and send it via present_files. This worked reliably every time it was used.
   - CRITICAL ORDERING RULE, learned the hard way: if a batch includes a NEW file that an EXISTING file depends on (e.g. Header.astro importing nav-tickets.json), tell the PM to upload the NEW file FIRST, before pasting the edit that references it. Getting this backwards caused a real, several-minutes-long broken production build (Header.astro referenced a file that didn't exist yet in the repo) — confirmed via git history + rebuilding each historical commit to pinpoint exactly which commit broke it and which one fixed it.

B. Verify GitHub's ACTUAL state before assuming a handoff worked, and before starting new work:
   - The PM copy-pastes by hand into a browser text box. This has gone wrong multiple times this session — most seriously, two separate incidents where one file's content got pasted into a DIFFERENT file's edit page (config.yml got overwritten with index.astro's content once; index.astro got overwritten with BUILD_LOG.md's content another time). Both times the fix was: clone the live repo fresh, diagnose the actual state (don't assume), and restore from the exact tested copy already sitting in this session's /mnt/user-data/outputs directory if it's still there — it usually is, within the same session.
   - ALWAYS start a new round of work with `git fetch origin main && git reset --hard origin/main`, then an actual `npm run build`, before touching anything. Don't assume the last handoff landed correctly just because the person said they uploaded it.
   - If a Cloudflare deploy screenshot shows red/failed builds, don't guess at the cause from the commit messages alone — clone fresh and try building each recent commit in sequence (`git checkout <hash> && npm run build`) to pinpoint exactly where it broke and exactly where it got fixed. This is fast and precise; guessing is not.

C. Test discipline (this was already established before this session and held up well — keep doing it):
   - Every content-driven feature gets an empty-safe test: blank the relevant CMS field(s), rebuild, confirm no crash and a clean fallback (not a broken empty element), then restore the exact original content and rebuild again, then diff the restored file against the pre-test backup to PROVE it's byte-identical before moving on.
   - Before presenting files, diff the /mnt/user-data/outputs copy against the actually-tested sandbox source file. Every single handoff this session included this diff-check and it caught nothing wrong when done — but skipping it is exactly how the corruption incidents in §3B went unnoticed as long as they did.
   - Check compiled/minified output, not just source, when confirming a CSS or JS fix actually took effect — several fixes this session (the CSS specificity issues in particular, see §5) required checking the actual generated CSS to catch what the source alone didn't reveal.
   - When a fix is genuinely site-wide (a shared component like Header.astro or Logo.astro), verify it rendered correctly on BOTH the homepage AND at least one unrelated inner page — the homepage and inner pages sometimes behave differently in ways that are easy to miss if you only check one.

D. Be honest about what can't be verified. Every build-log entry this session ends with a "NOT verifiable by me" line naming the specific thing that needs the PM's own eyes (an actual on-screen look, a real click-through, a real narrow-screen test). Keep doing this — it's what let problems get caught and reported precisely rather than vaguely.

5. TECHNICAL NOTES WORTH KNOWING BEFORE TOUCHING RELATED CODE
============================================================
- **Astro CSS specificity gotcha**: Astro auto-appends its own scoping attribute selector to EVERY class in a compound/descendant selector, not just the last one. This means a rule like ".nav-wide .pill" can end up with MORE effective specificity than a naive reading of "two classes vs one" would suggest, and can silently beat a more "specific-looking" override elsewhere in the same file. This caused a real bug (the Tickets button rendering as a plain white pill instead of blue) that took real debugging to trace. The reliable fix used twice now: `!important` on the specific properties that need to win, rather than trying to out-calculate Astro's specificity math. See .tickets-btn and .calendar-btn in Header.astro for the working pattern (and the code comments explaining why).
- **The site-wide `img { max-width: 100% }` reset** (in global.css) exists to stop images overflowing their containers, but it can silently fight with an image that also has a fixed height + auto width (used for aspect-ratio-correct logo scaling) — if the image's flex container ever gets squeezed narrower than the image needs, max-width clamps the width down while the height stays fixed, visibly distorting the image. Fixed for the logo specifically via `flex-shrink: 0` on its wrapping element (Logo.astro) — if any OTHER fixed-aspect-ratio image elsewhere on the site ever exhibits similar squashing in a tight flex layout, this is the same failure mode and the same fix applies.
- **`flex-wrap: wrap` as a "just in case" safety net is risky**, not free — it was added defensively to the header this session and caused a real regression (forced the whole nav onto two rows even where everything fit fine on one). Prefer a targeted fix (protect the specific element that actually breaks) over a broad layout-level safety net, unless there's a demonstrated, specific case that needs it.
- **Empty-array truthiness in Astro/JS**: `array ?` is TRUE even for an empty array `[]`, which caused a real bug (an empty Tickets dropdown still rendering a dead-looking empty box). Use `array && array.length > 0` when the intent is "has at least one item," not just `array`.
- **Card grids / lists that need to react to whichever item is LAST** (used for a since-removed star trail feature, but the technique is sound and may be useful again): mark the last item via `i === array.length - 1` in the `.map()`, rather than hardcoding a position — this correctly follows content reordering automatically.
